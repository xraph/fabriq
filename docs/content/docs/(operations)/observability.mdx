Point an OTLP collector at the app and you get traces. Scrape two endpoints
and you get metrics. Both live on `FABRIQ_HTTP_ADDR` (default `:8081`):

| Path | What it serves |
| --- | --- |
| `/metrics` | fabriq's own Prometheus registry. Every series is named `fabriq_*`, with no `forge_` prefix. |
| `/_/metrics` | forge's registry: HTTP server metrics, and grove's `db_client_operation_duration_seconds` for the databases fabriq dials. |

```bash
curl localhost:8081/metrics     # fabriq_* series
curl localhost:8081/_/metrics   # forge HTTP + grove db_client_* series
```

fabriq mounts `/metrics` when forge calls the extension's `Run`, after every
extension has started, so every node that opens the facade serves it, worker
or not. If your app already owns `GET /metrics`, fabriq logs a warning and its
series are recorded but not served. `/metrics` sits on the same listener as
forge's `/_/metrics` with the same exposure: no auth of its own, so keep that
port off the internet (the Helm Service is `ClusterIP`).

## Traces

Spans go to the global OpenTelemetry tracer provider, which `forge.New`
installs. Spans fabriq's core starts carry the instrumentation scope
`github.com/xraph/fabriq/core`; spans the root module starts carry
`github.com/xraph/fabriq`. You don't configure anything in fabriq to get
them. forge already traces every HTTP request, and grove v1.8.0 adds a
`db.client` span for every query under whichever fabriq span is active.

| Span | Kind | Starts | Attributes |
| --- | --- | --- | --- |
| `execute command` | Internal, child of the caller | every `Exec` / `ExecBatch` | `fabriq.command.op` (`create`, `update`, `delete`, `upsert`, `mixed`), `fabriq.batch_size`, `fabriq.entity` (when the batch writes one entity), `fabriq.result` |
| `publish outbox batch` | Producer, new root | each relay batch that found rows | `messaging.system=redis`, `messaging.batch.message_count`; a link to the span that wrote each row (up to 128) |
| `apply projection event` | Consumer, new root | each envelope the graph, search, analytics and insights consumers apply | `fabriq.projection`, `messaging.consumer.group.name`, `fabriq.entity`, `fabriq.mutations` (graph and search); a link to the writer |
| `embed event` | Consumer, new root | each envelope for an entity with an `Embed` spec | `messaging.consumer.group.name=proj:embed`, `fabriq.entity`, `fabriq.embed.skipped` (poison payload); a link to the writer |
| `call embedder`, `call summarizer` | Internal | every model call `core/agent` makes | `fabriq.model.kind` (`embed`, `summarize`), `fabriq.model.inputs` |
| `recall context` | Internal | `Toolkit.Recall` | `fabriq.recall.entities`, `fabriq.recall.budget`, `fabriq.recall.items`, `fabriq.recall.omitted` |
| `materialize document` | Internal, new root | each quiet document the document plane materializes | `fabriq.entity`, `fabriq.document.materialized` |
| `compact document` | Internal, new root | each document due for compaction | `fabriq.entity` |
| `reconcile projection` | Internal, new root | each tenant and projection, every reconcile interval | `fabriq.projection`, `fabriq.reconcile.drifts` |
| `collect blob garbage` | Internal, new root | each tenant, every reconcile interval | `fabriq.blob.bytes_freed`, `fabriq.blob.collected`, `fabriq.blob.refs_corrected`, `fabriq.blob.orphans_deleted`, `fabriq.blob.broken` |
| `maintain rollup` | Internal, new root | each tenant and materialized metric, every rollup interval | `fabriq.metric` |
| `enforce analytics retention` | Internal, new root | the hourly retention run | `fabriq.analytics.events_pruned` |
| `distill tenant` | Internal, new root | each debounced distill sweep | `fabriq.distill.refs`, `fabriq.distill.failures`; a link to the writer of each envelope it covers (up to 128) |
| `run admin job` | Internal, new root | each async admin job (analytics backfill, reconcile and reproject, migrations, tenant provisioning) | `fabriq.job.kind`; a link to the request that started it |

`fabriq.result` on `execute command` is `ok`, `invalid` (no tenant, or the
command failed validation), `conflict`, `not_found` or `error`. Only `error`
marks the span failed. `fabriq.command.op` is `unknown` for an op value the
executor doesn't define, and such a command is always `invalid`.

`remote/grpc` traces every RPC with otelgrpc: a Client span from `Dial`, and a
Server span from `ServerOptions` (and so `NewServer`) that continues the
caller's trace. The reference `fabriqserver` binary installs no tracer
provider, so its spans are no-ops until you add one.

### What reaches a span, and what doesn't

The spans fabriq starts carry no tenant IDs, no aggregate, event, document or
node IDs, no payloads, no query or recall text, no SQL, DSNs or bearer keys. A
failed span's status description is a short class (`apply failed`, `publish
failed`), and its `exception` event carries only `exception.type`. Error text
never gets copied, because driver messages quote values. A rejected gRPC
credential gets the fixed status message `remotegrpc: unauthenticated` for
the same reason.

grove's own `db.client` spans, which sit under fabriq's, carry more: the
database name as `db.namespace` and the first table as `db.collection.name`
and `db.query.summary`. In catalog mode those name the tenant. With database
isolation each tenant's database is `fabriq_<tenantID>`; with schema
isolation the table is written `tenant_<id>.fabriq_crdt_docs`. They are opaque
resource identifiers, which the telemetry rules allow on spans and never on
metric labels: the metric side drops or bounds them (below).

The entity name (`fabriq.entity`) is on spans but never on a metric label:
runtime dynamic entities make it unbounded.

### Across the outbox

The executor stamps the `execute command` span's W3C `traceparent` into the
envelope and the `fabriq_outbox.traceparent` column, as it always has. What
changed is how the far side uses it. The request that wrote the command has
usually finished long before its event is published or applied, so the relay
and every consumer start a **new root span** and **link** it to that stored
context. You follow the link from a projection apply back to the command
that caused it; you don't get one trace that stays open across the hop.

Background loops (the relay, the consumers, the sweeper, the document plane,
the live-query feed, the L1 evict tailer) drop the span they were started
under, so an idle poll never files a query under forge's boot trace or an
ended request. They only start a span when there's work.

## Metrics on `/metrics`

All of these are on fabriq's private registry. The names are exact. Every
node serves the registry, but some series are only fed by the worker: the
outbox backlog, consumer lag, relay, analytics, embed, distill, blob GC,
sweep, pool and restart series read zero on a node that doesn't run it, so
point those alerts at worker pods. Command latency, conflation depth and
backstop trips are measured on every node.

| Metric | Type | Labels | Meaning |
| --- | --- | --- | --- |
| `fabriq_command_duration_seconds` | histogram | `op` (`create`, `update`, `delete`, `upsert`, `mixed`, `unknown`), `result` (`ok`, `invalid`, `conflict`, `not_found`, `error`) | One command batch, validation through commit. Every node. |
| `fabriq_relay_batch_duration_seconds` | histogram | `result` (`ok`, `error`) | One outbox batch the relay published. Empty polls aren't observed. |
| `fabriq_projection_apply_duration_seconds` | histogram | `projection` (`graph`, `search`, `analytics`, `insights`), `result` (`ok`, `error`) | Applying one envelope. Skipped envelopes aren't observed. |
| `fabriq_model_call_duration_seconds` | histogram | `kind` (`embed`, `summarize`), `result` (`ok`, `error`) | One Embedder or Summarizer call by the embed and distill workers. |
| `fabriq_worker_restarts_total` | counter | `runner` (`relay`, `document-plane`, `reconciler`, `blob-gc`, `rollup:insights`, `proj:graph`, `proj:search`, `proj:analytics`, `proj:insights`, `proj:embed`, `proj:distill`, `sweeper`, `sweeper:wake`) | A background runner exited and the supervisor restarted it. Per-shard relays all count as `relay`. |
| `fabriq_outbox_backlog` | gauge | | Unpublished outbox rows, summed across shards every 15s. Worker only. |
| `fabriq_relay_published_total` | counter | | Events the relay published. |
| `fabriq_projection_lag_events` | gauge | `projection` (`graph`, `search`) | Entries the consumer group hasn't acknowledged (lag plus pending), every 15s. Worker only. |
| `fabriq_tenant_hook_trips_total` | counter | | Tenant-guard backstop trips in this process, read at scrape time on every node. Must stay zero. Static and sharded deployments; catalog mode's pooled tenant adapters aren't summed. |
| `fabriq_conflation_depth` | gauge | | Deltas buffered in this node's subscription hub, read at scrape time. |
| `fabriq_analytics_applied_total` | counter | | Envelopes the `proj:analytics` consumer applied. |
| `fabriq_analytics_failures_total` | counter | | Envelopes it failed to apply (left pending for redelivery). |
| `fabriq_analytics_lag_seconds` | gauge | | The stalest tenant's analytics lag, sampled every 15s. |
| `fabriq_analytics_tenants_behind` | gauge | | Tenants whose analytics lag is past 60s. |
| `fabriq_analytics_events_pruned_total` | counter | | History events the retention run deleted. |
| `fabriq_embed_events_total` | counter | | Events the embed worker handled (indexed or ack-skipped). |
| `fabriq_embed_failures_total` | counter | | Events it failed to index (left pending). |
| `fabriq_distill_nodes_total`, `fabriq_distill_summaries_total`, `fabriq_distill_shortcircuit_total`, `fabriq_distill_guard_blocked_total`, `fabriq_distill_failures_total`, `fabriq_distill_splits_total`, `fabriq_distill_dedup_total`, `fabriq_distill_intermediate_gc_total` | counter | | The distill worker's work, see [Distillation](/docs/distillation). |
| `fabriq_blob_gc_bytes_freed_total`, `fabriq_blob_gc_collected_total`, `fabriq_blob_gc_ref_drift_corrected_total`, `fabriq_blob_gc_orphans_total` | counter | | Blob GC work, see [Blob GC](/docs/blob-gc). |
| `fabriq_blob_gc_broken` | gauge | | Referenced hashes with missing bytes, last GC cycle. |
| `fabriq_sweep_pass_duration_seconds` | histogram | | One catalog sweep pass (catalog mode). |
| `fabriq_sweep_tenants_tracked`, `fabriq_sweep_tenants_eligible` | gauge | | The sweeper's backoff table and eligible tenants. |
| `fabriq_sweep_swept_total`, `fabriq_sweep_busy_total`, `fabriq_sweep_errors_total` | counter | | Tenant passes dispatched, that found work, and that failed. |
| `fabriq_pool_shards_open`, `fabriq_pool_shards_held`, `fabriq_pool_cap` | gauge | | Catalog-mode tenant pools open, in use, and the current cap. |
| `fabriq_pool_scale_events_total` | counter | `direction` (`grow`, `shrink`) | Adaptive pool cap decisions. |
| `fabriq_catalog_read_primary_total`, `fabriq_catalog_read_replica_total`, `fabriq_catalog_read_failover_total` | counter | | Routing catalog reads by where they were served, read at scrape time. Zero without catalog replicas. |

<Callout type="error">
`fabriq_tenant_hook_trips_total` is a correctness alarm, not a capacity one. A
non-zero value means a query reached an engine without tenant scoping. RLS
contained the blast radius, but the call site has to be found and fixed. Page
the owning team. See [Runbooks](/docs/runbooks).
</Callout>

### Changes in v1.8.0

If you have dashboards on the older series, four things moved:

- `fabriq_projection_lag_events` lost its `tenant` label, which was always
  `_all`. Match on `projection` alone.
- `fabriq_catalog_read_*_total` are counters now (they were gauges holding
  cumulative values), so `rate()` works on them.
- `fabriq_conflation_depth` used to be registered and never set. It now
  reports the hub's real buffered count.
- `fabriq_tenant_hook_trips_total` is read at scrape time on every node, so
  trips on API nodes (where they happen) finally show up.

## Metrics on `/_/metrics`

forge owns this registry. fabriq hands `app.Metrics()` to every grove
database and KV store it opens: the Postgres shards, the catalog and its
replicas, schema-isolation consolidation databases, the Postgres analytics
sink and the Redis cache. grove then records:

| Metric | Type | Labels |
| --- | --- | --- |
| `db_client_operation_duration_seconds` | histogram | `db_system_name` (`postgresql`, `redis`), `db_namespace`, `db_operation_name`, `db_collection_name`, `db_response_status_code`, `error_type` |

Two labels need care, and fabriq handles both. `db_collection_name` is
grove's first table in the statement, which would otherwise grow with every
schema-isolation tenant, every dynamic entity and any table name a tenant
puts in raw analytics SQL. fabriq strips the schema qualifier and keeps the
name only for its system tables, static entity tables and rollup tables;
everything else is `other`. `db_namespace` is the database name, so tenant
databases in database-isolation catalog mode get no sink at all (there the
database is the tenant). Their queries are still traced. A `*grove.DB` that
fabriq borrows from your container keeps whatever sink you gave it.

forge's own HTTP server metrics are on the same endpoint. fabriq doesn't
measure its own Redis Streams, Elasticsearch or ClickHouse client calls
separately; the fabriq spans above cover that work.

## Health endpoints

forge serves three health endpoints on the same address:

| Path | Use |
| --- | --- |
| `/_/livez` | Liveness: the process is up. Kubernetes liveness probe. |
| `/_/readyz` | Readiness: ready to serve. Kubernetes readiness probe. |
| `/_/health` | Aggregate health detail, including the worker's store ping. |

The worker's health check pings Postgres through grove. It reports unhealthy
if the stores aren't open.

## Scraping

The Helm chart adds `prometheus.io/scrape` pod annotations by default. They
can name only one path, so they cover `/metrics`. Enable the ServiceMonitor
(`metrics.serviceMonitor.enabled`) and it scrapes both `/metrics` and
`/_/metrics` on the `http` port (`metrics.forgeEndpoint`, on by default). See
[Deployment](/docs/deployment).

For lag-driven autoscaling of projection consumers, drive a KEDA scaler off
Redis stream lag or `fabriq_projection_lag_events` and not CPU. The singleton
runners are leader-elected and don't scale with replica count, but the
consumers do.
