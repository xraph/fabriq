Fabriq ships as **one binary**, `fabriq`, built from `cmd/fabriq` on
forge/cli `RunApp`. The same image is the long-lived worker and the one-shot
operator commands — both share one wiring path.

- `fabriq serve` (also the no-arg default) runs the background plane: the
  leader-elected outbox relay, projection consumers, the reconciler, and the
  CRDT document plane. This is what the container ENTRYPOINT runs.
- `fabriq migrate | inspect | rebuild | reconcile` are operator commands that
  open their own stores from flags/env and exit. They never serve.
- `fabriq info | health | extensions` are forge built-ins.

There is no separate worker binary. See [CLI](/docs/cli) for the
full command surface.

<Callout type="info">
This page covers running the standalone `fabriq` image. When fabriq is
**embedded as a library** (`fabriq.Open` inside a host application), the same
binary concerns do not apply, but the tenancy contract does — a host that
serves one customer per process pins its tenant at the boundary. See
[Single-tenant-per-instance deployments](/docs/tenancy#single-tenant-per-instance-deployments)
for the seam and the shared-database vs database-per-instance trade-offs.
</Callout>

## Releases & published artifacts

Every `vX.Y.Z` git tag publishes three things via GitHub Actions
([`.github/workflows/release.yml`](https://github.com/xraph/fabriq/blob/main/.github/workflows/release.yml),
driven by [goreleaser](https://github.com/xraph/fabriq/blob/main/.goreleaser.yaml)):

- **Container image** — multi-arch (`linux/amd64`, `linux/arm64`) on GHCR:

  ```bash
  docker pull ghcr.io/xraph/fabriq:0.2.0   # also :0.2 and :latest
  ```

- **Helm chart** — pushed as an OCI artifact and attached to the release:

  ```bash
  helm install fabriq oci://ghcr.io/xraph/charts/fabriq --version 0.2.0 \
    --set postgres.existingSecret=pg-conn --set redis.addr=redis:6379
  ```

- **Binaries** — `linux`/`darwin` × `amd64`/`arm64` archives plus
  `checksums.txt` on the [GitHub Release](https://github.com/xraph/fabriq/releases),
  for running the operator CLI (`fabriq migrate`, `inspect`, …) off-cluster.

Cutting a release is just a tag — `git tag v0.2.0 && git push origin v0.2.0`.
Pre-release suffixes (`v0.2.0-rc.1`) are auto-marked pre-release. Versions are
stamped into the binary (`fabriq --version`) and the image's OCI labels.

## The image

The Dockerfile builds a single static, stripped binary and ships it on
`distroless/static-debian12:nonroot`. The ENTRYPOINT is `fabriq serve`; the
migrate Job overrides the command.

```dockerfile
FROM golang:1.26 AS build
WORKDIR /src
COPY go.mod go.sum ./
COPY vendor/ vendor/
COPY . .
RUN CGO_ENABLED=0 GOFLAGS=-mod=vendor go build -trimpath -ldflags "-s -w" \
      -o /out/fabriq ./cmd/fabriq

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/fabriq /usr/local/bin/fabriq
USER nonroot:nonroot
EXPOSE 8081
ENTRYPOINT ["/usr/local/bin/fabriq", "serve"]
```

<Callout type="warn">
The build is **hermetic from a vendored tree**. The repo carries local grove
`replace` directives pointing outside this checkout (until grove cuts a tagged
release), so a plain `docker build` cannot resolve them. Build through the
Makefile, which runs `go mod vendor` first:

```bash
make docker-build   # = go mod vendor, then docker build -f deploy/docker/Dockerfile
```

Vendoring is harmless once the replaces are dropped, so the Dockerfile keeps
working unchanged after the grove tag.
</Callout>

## The Helm chart

The chart in `deploy/helm/fabriq` deploys the worker Deployment plus a
schema-migration Job. **Datastores are external** — the chart bundles no
databases. Point it at managed Postgres+Timescale, Redis, and (optionally)
FalkorDB and Elasticsearch.

<Steps>
<Step>
Configure datastore connections. Each store has its own values block. Only
the Postgres DSN is sensitive (it carries credentials); Redis, FalkorDB and
Elasticsearch are plain addresses. For production, reference Secrets you (or
an operator like CloudNativePG / External Secrets) already manage:

```yaml
# Postgres: read a full DSN from a managed Secret key (e.g. "uri").
postgres:
  existingSecret: pg-conn
  dsnKey: uri
redis:
  addr: redis-master:6379          # or redis.existingSecret + addrKey
# Optional projection planes — enabling one REQUIRES its connection, and the
# chart fails the install if it is missing.
projections:
  search: true
elasticsearch:
  existingSecret: es-conn
```

Alternatively, compose Postgres from parts with the password pulled from a
Secret (the chart builds a `$(VAR)` reference so the password never leaves
its Secret), or set `postgres.dsn` inline for dev/CI (the chart then creates
its own Secret rather than putting the DSN in a ConfigMap):

```yaml
postgres:
  host: pg.internal
  user: fabriq_app
  database: fabriq
  sslmode: require
  passwordSecret: rds-creds        # an existing Secret
  passwordKey: password
```

The connection env the worker and migrate Job resolve is `FABRIQ_POSTGRES_DSN`
(required), `FABRIQ_REDIS_ADDR` (required for projections and subscriptions),
`FABRIQ_FALKORDB_ADDR` (graph projection), and `FABRIQ_ELASTICSEARCH_ADDRS`
(comma-separated; search projection).
</Step>

<Step>
Install or upgrade. The migrate Job runs first as a `pre-install,pre-upgrade`
hook, so the schema is current before the worker rolls.

```bash
helm upgrade --install fabriq deploy/helm/fabriq \
  --set postgres.existingSecret=pg-conn --set postgres.dsnKey=uri \
  --set redis.addr=redis-master:6379
```
</Step>

<Step>
Watch it come up and confirm health.

```bash
kubectl rollout status deploy/fabriq
kubectl port-forward svc/fabriq 8081:8081
curl localhost:8081/_/readyz
curl localhost:8081/metrics     # fabriq_* series
curl localhost:8081/_/metrics   # forge HTTP + grove db_client_* series
```
</Step>
</Steps>

### Migration Job (pre-upgrade hook)

When `migrate.enabled` (default `true`), the chart renders a Job annotated
`helm.sh/hook: pre-install,pre-upgrade` that overrides the container command
to `fabriq migrate up`. grove holds an advisory migration lock, so parallel
hook runs across releases are safe. The Job resolves the same connection env
as the worker but uses only the Postgres DSN. If you disable the hook, you
must run `fabriq migrate up` yourself before the worker serves traffic. See
[Migrations](/docs/migrations).

### Worker Deployment

The worker container uses the image ENTRYPOINT (`fabriq serve`) — the chart
does not override the command. It runs as non-root with a read-only root
filesystem (a `/tmp` `emptyDir` is mounted writable) and drops all
capabilities.

Config splits across two sources, both injected as env:

- **Connection env** — the datastore connections above, rendered per store as
  `valueFrom.secretKeyRef` (managed Secrets), a `$(VAR)`-composed DSN, or a
  plain value. Inline dev credentials land in a chart-created Secret rather
  than a ConfigMap.
- **ConfigMap** — non-secret tuning: `FABRIQ_HTTP_ADDR` (default `:8081`) and
  `FABRIQ_RECONCILE_INTERVAL` (Go duration; empty uses the binary default of
  5m, `0` disables the scheduled reconciler). Extra plain env merges via
  `config.extraEnv`.

A pod-template checksum annotation rolls the workers when the ConfigMap (or
the chart-created Secret, when inline credentials are used) changes.

### Health probes and metrics

Forge serves health and metrics on `FABRIQ_HTTP_ADDR` (default `:8081`,
chart `service.port`):

| Path | Use |
| --- | --- |
| `/_/livez` | Liveness probe (chart: `periodSeconds: 15`). |
| `/_/readyz` | Readiness probe (chart: `periodSeconds: 10`). |
| `/_/health` | Aggregate health detail. |
| `/metrics` | Prometheus scrape: fabriq's own `fabriq_*` series (mounted by fabriq). |
| `/_/metrics` | Prometheus scrape: forge's HTTP metrics and grove's `db_client_operation_duration_seconds`. |

The Service is `ClusterIP` and not internet-facing. See
[Observability](/docs/observability) for the metric catalog and the spans.

### Scaling model

The worker is **safe to scale** (chart default `worker.replicaCount: 2`):

- **Singletons are leader-elected** via Postgres advisory locks, so exactly
  one replica runs each: the outbox relay (lock `1001`), the reconciler
  (`1002`), and the document plane materializer (`1003`). Extra replicas
  campaign and stand by. A leader that loses its Postgres session abdicates;
  another replica wins the next campaign.
- **Projection consumers scale by replica count.** The graph and search
  consumers share Redis Streams consumer groups (no election), so apply
  throughput grows with replicas.

The chart includes:

- **PDB** (`pdb.enabled`, `minAvailable: 1`) — keeps a replica during
  voluntary disruptions so a leader is always available.
- **HPA** (`autoscaling.enabled`, CPU target) — optional. For lag-driven
  scaling of consumers, prefer KEDA on Redis stream lag or
  `fabriq_projection_lag_events` rather than CPU.
- **ServiceMonitor** (`metrics.serviceMonitor.enabled`): scrapes `/metrics`
  and, while `metrics.forgeEndpoint` is on (the default), `/_/metrics` on the
  `http` port for a Prometheus Operator install. Without it, the chart adds
  `prometheus.io/scrape` pod annotations by default; they can name one path,
  so they cover `/metrics` only.
- **NetworkPolicy** (`networkPolicy.enabled`) — allows ingress to the http
  port (scrape + health) and DNS egress; you supply datastore egress peers in
  `networkPolicy.egress`.

The worker drains on SIGTERM (~10s); the chart sets
`terminationGracePeriodSeconds: 30` for headroom.

### Sharded deployments

The chart's connection values render a single `FABRIQ_POSTGRES_DSN`, so out of
the box they configure a **one-shard** deployment. To shard the source of truth
across multiple Postgres instances ([Sharding](/docs/sharding)), supply a
`config.yaml` carrying a `shards:` list — the `FABRIQ_*` environment overlay
cannot express a list of shards. Mount it (for example a ConfigMap at
`/etc/fabriq/config.yaml`), and run the migrate step **once per shard DSN**:
`fabriq migrate` targets one database at a time. The shard count is fixed at
deploy time.

## Bare deployment (without Helm)

Run the same image anywhere with the env vars set:

```bash
docker run --rm \
  -e FABRIQ_POSTGRES_DSN='postgres://app:...@pg:5432/fabriq?sslmode=require' \
  -e FABRIQ_REDIS_ADDR='redis:6379' \
  -e FABRIQ_FALKORDB_ADDR='falkordb:6379' \
  -e FABRIQ_ELASTICSEARCH_ADDRS='https://es:9200' \
  -p 8081:8081 \
  ghcr.io/xraph/fabriq:latest          # ENTRYPOINT runs `fabriq serve`
```

Run migrations as a discrete step first, as the schema owner:

```bash
docker run --rm --entrypoint /usr/local/bin/fabriq \
  -e FABRIQ_POSTGRES_DSN='postgres://owner:...@pg:5432/fabriq' \
  ghcr.io/xraph/fabriq:latest migrate up
```

## Hosted server

`fabriq serve` can run as a standalone server that other services call over HTTP with a key. You turn the admin API on, give it one operator key, and issue a key per service from there. You don't write any Go. This section is the whole contract: the two database roles, the run order, every environment variable, and what the probes mean.

<Callout type="info">
The Helm chart deploys the worker only. It doesn't mount the admin API and has no value that injects a Secret-backed `FABRIQ_ADMIN_KEY`, so run a hosted server from the image directly. The [chart README](https://github.com/xraph/fabriq/blob/main/deploy/helm/fabriq/README.md) lists what it can and can't do.
</Callout>

### Two roles, four steps

You need two Postgres roles. A privileged one (a superuser, or any role that can `CREATE EXTENSION`) runs the setup commands. A second role, `fabriq_app`, serves traffic. They are separate because row-level security is the only tenant fence behind the admin API, and a superuser or a `BYPASSRLS` role walks straight past it. With the admin API on, `serve` refuses to start as such a role. `FABRIQ_ALLOW_RLS_BYPASS=true` overrides the check, and you should only ever set it on a laptop.

Run the steps in this order, and stop at the first non-zero exit. The image's entrypoint is `fabriq serve`, so the one-shot commands below pass `--entrypoint` to `docker run`. In Kubernetes you'd set `command` on the Job instead.

<Steps>
<Step>
Check the database has what fabriq needs. Preflight wants `timescaledb`, `vector` and `postgis`, and `timescaledb` has to be in `shared_preload_libraries`. The `timescale/timescaledb-ha:pg16-all` image has all three.

```bash
docker run --rm --entrypoint /usr/local/bin/fabriq \
  -e FABRIQ_POSTGRES_DSN="$PRIVILEGED_DSN" \
  ghcr.io/xraph/fabriq:1.9.0 migrate preflight --json
```

It exits 0 when everything is there, 4 when an extension is missing or `timescaledb` isn't preloaded, and 1 when it can't connect or query. Don't skip it. `migrate up` quietly leaves out the pgvector and PostGIS tables when those extensions are missing, and you'd find out later.

The JSON report has this shape (trimmed to one extension here):

```json
{"ok":true,"extensions":[{"name":"timescaledb","available":true,"installed":"2.17.2","preloaded":true,"ok":true}],"problems":[]}
```

Use `--require a,b` to check a different set.
</Step>

<Step>
Apply the migrations with the privileged DSN. The command takes an advisory lock, so running it from several places at once, or on every release, is safe.

```bash
docker run --rm --entrypoint /usr/local/bin/fabriq \
  -e FABRIQ_POSTGRES_DSN="$PRIVILEGED_DSN" \
  ghcr.io/xraph/fabriq:1.9.0 migrate up
```

On an upgrade, do this before you roll out the new binaries. Version 1.9.0 adds two tables (`fabriq_dynamic_entity` and `fabriq_tenant`) and a `last_used_at` column on `fabriq_api_key`. The code copes with a database that hasn't got the last two yet, but with persistence on (the default) it needs `fabriq_dynamic_entity`.
</Step>

<Step>
Create the serving role. The password comes from the environment and nowhere else, so it never shows up in a process listing.

```bash
docker run --rm --entrypoint /usr/local/bin/fabriq \
  -e FABRIQ_POSTGRES_DSN="$PRIVILEGED_DSN" \
  -e FABRIQ_APP_ROLE_PASSWORD="$APP_ROLE_PASSWORD" \
  ghcr.io/xraph/fabriq:1.9.0 migrate app-role --role fabriq_app
```

The role is created, or reset if it exists, as `LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION`. It gets `USAGE` and `CREATE` on schema `public`, DML on every table and sequence, and default privileges for the ones created later. Running the command again rotates the password and strips any attribute the role picked up since.

It exits 2 for a usage problem (no `--role`, no `FABRIQ_APP_ROLE_PASSWORD`, a bad role name, or a role equal to the one the DSN connects as) and 1 for a database error. One caveat: if your server runs with `log_statement` set to `ddl` or `all`, Postgres may write the password to its log.
</Step>

<Step>
Start the server with the `fabriq_app` DSN.

```bash
docker run -d --name fabriq -p 8081:8081 \
  -e FABRIQ_POSTGRES_DSN='postgres://fabriq_app:...@pg:5432/fabriq?sslmode=require' \
  -e FABRIQ_REDIS_ADDR=redis:6379 \
  -e FABRIQ_ADMIN_API=true \
  -e FABRIQ_ADMIN_KEY="$FABRIQ_ADMIN_KEY" \
  -e FABRIQ_DOMAIN_PACK=none \
  ghcr.io/xraph/fabriq:1.9.0
```

If it can't start, it exits 1 with a message naming the cause: an unmigrated database, a missing or malformed `FABRIQ_ADMIN_KEY`, a role that bypasses RLS, or a bad value in one of the variables below.
</Step>
</Steps>

### Environment

| Variable | Required | Default | Meaning |
| --- | --- | --- | --- |
| `FABRIQ_POSTGRES_DSN` | yes | | The serving DSN, for the `fabriq_app` role. |
| `FABRIQ_REDIS_ADDR` | yes | | `host:port`. |
| `FABRIQ_REDIS_USERNAME`, `FABRIQ_REDIS_PASSWORD` | no | | Redis ACL user and password. |
| `FABRIQ_FALKORDB_ADDR` | no | | `host:port`. Turns the graph projection on. |
| `FABRIQ_FALKORDB_USERNAME`, `FABRIQ_FALKORDB_PASSWORD` | no | | FalkorDB credentials. |
| `FABRIQ_ELASTICSEARCH_ADDRS` | no | | Comma-separated URLs. Turns search on. |
| `FABRIQ_ELASTICSEARCH_USERNAME`, `FABRIQ_ELASTICSEARCH_PASSWORD` | no | | Elasticsearch basic-auth credentials. |
| `FABRIQ_HTTP_ADDR` | no | `:8081` | Listen address for everything. |
| `FABRIQ_RECONCILE_INTERVAL` | no | `5m` | A Go duration. `0` turns the scheduled reconciler off. |
| `FABRIQ_ADMIN_API` | no | `false` | `true` mounts the admin API under `/admin` with key auth. |
| `FABRIQ_ADMIN_KEY` | with the admin API | | The bootstrap operator key, matching `^fq_[0-9A-Za-z]{32,}$`. Ensured at every start as a multi-tenant key that can manage keys. |
| `FABRIQ_ADMIN_LOGIN_USER`, `FABRIQ_ADMIN_LOGIN_PASSWORD` | no, as a pair | unset | Enable `POST /admin/login` for the dashboard. Unset means no password login at all. |
| `FABRIQ_DOMAIN_PACK` | no | `example` | `none` registers no demo entity types. Use it on a hosted server. |
| `FABRIQ_DYNAMIC_PERSIST` | no | `true` | Persist runtime-defined entity types and reload them at start. |
| `FABRIQ_DYNAMIC_SYNC_INTERVAL` | no | `15s` | How often a process picks up types another process defined. |
| `FABRIQ_ALLOW_RLS_BYPASS` | no | `false` | Development only. Lets `serve` run as a superuser. |

A few rules about how these behave:

- A non-empty environment variable beats the same setting in `config.yaml`. That includes all six credential variables.
- The admin-only variables (`FABRIQ_ADMIN_API`, the login pair and `FABRIQ_ALLOW_RLS_BYPASS`) are checked when the server starts. A bad one makes `fabriq serve` exit 1 and name the variable, while every other command ignores them. A bad value in any other variable fails every command.
- The login password can't be longer than 72 bytes (a bcrypt limit), and there is no default login. Leave the pair unset and nobody can log in with a password.
- `fabriq serve` replaces any `dynamic:` block in `config.yaml` with the values above. In [catalog mode](/docs/tenancy) it keeps persistence off whatever `FABRIQ_DYNAMIC_PERSIST` says.
- `migrate` doesn't read any `FABRIQ_ADMIN_*` variable.

### One port, two probes

Everything listens on `8081`: the admin API under `/admin`, the probes, `/metrics` (fabriq's own series) and `/_/metrics` (forge's).

| Path | Answers |
| --- | --- |
| `GET /_/livez` | 200 `{"status":"alive"}` whenever the process is serving HTTP. |
| `GET /_/readyz` | 200 `{"status":"ready"}` when the facade is open (migrations applied, persisted entity types loaded), Postgres answers a ping, Redis answers a ping if you configured it, and, with the admin API on, the bootstrap key has been ensured. Otherwise 503 `{"status":"not ready","reason":"..."}`. |

Each readiness check gets two seconds, and there is no startup grace period. Point your orchestrator at these two and ignore forge's `/_/health/*`, which reports ready for the first 60 seconds whatever the state of the stores.

A wrong engine password at boot stops the process with an error that names the engine. A credential that goes bad later turns `/_/readyz` into a 503 with a reason naming it. That reason echoes the driver's error (never the password), so keep `:8081` on a private network.

### Keys and tenants

The operator key in `FABRIQ_ADMIN_KEY` is for your control plane. Use it to register tenants on `POST /admin/tenants` and to issue keys on `POST /admin/keys`. The usual pattern is one multi-tenant key per consuming service, issued without a `tenantId`, with `canManageKeys` off. The service picks its tenant per request. See [Authentication](/docs/authentication) for the full route list and [Connection string](/docs/connection-string) for how a client uses the key.

To rotate the operator key, set the new value and restart, which ensures the new key. Then revoke the old key's id with `DELETE /admin/keys/:id`. Don't revoke the key that is still in `FABRIQ_ADMIN_KEY`: that locks the operator out until the variable changes and the server restarts.

### The admin console image

The console ships as its own image, `ghcr.io/xraph/fabriq-admin:0.1.0` (`linux/amd64` and `linux/arm64`), listening on `8080`. Point `FABRIQ_ADMIN_UPSTREAM` at the server's private address and give it a key, and the container proxies `/admin/` there. Never route it publicly. The variables, the key to use and a Compose example are on the [Admin Console](/docs/admin-console#running-the-container-image) page.
